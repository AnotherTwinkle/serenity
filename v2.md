# Serenity

Serenity enables any linux device on the same network to directly talk with each other. Serenity defines the SLPCP (Serenity Local P2P Comms Protocol).

## Serenity Communications Protocol

This section will outline the workings of SLPCP.

SLPCP works only on devices on the same wifi network. There is no hard distinction between a client or server, all protocols are designed to facitilate bidirectional comms by default, but connections can be limited virtually to a traditional client server model.

### Discovery

Serenity makes the use of zeroconf to announce device presence on a network. There is no specific identifier to seperate a Serenity-advertised device. The discoverer pings a particular route of all available devices on network, looking for a device that supports the serenity protocol.

Each device hosts a http server (by default on port 2406), the address of this server is the address advertised by serenity on zeroconf. 
This server has a route `/serenity/node`. This is the endpoint that other nodes use to determine the parameters of the serenity protocol this device supports. The response structure looks as follows-

```json
# Node Identity Structure
{
	"uid" : "An uid for the node. This may be generated using device specific seeds",
	"version" : "serenity version",
	"platform" : "android/linux/[windows?]",
	"connection_modes" : ["A list of protocols supported by this node"],

}
```

When a node discovers another node, it may initiate the connection if the other node's uid is higher than its own.

To initate a connection, a node may send a request to `/serenity/authenticate` with the same json node identity structure it broadcasts, along with a password for the target node (this is manually stored).

Both nodes will now be connected in the default bidirectional rest-p2p mode. The server will respond with parameters for the connection and a list of available commands for that node over that particular connection mode.

### Connection Modes

Serenity uses the same command and response structure for any connection mode. Although some commands and capabilities are limited to certain modes. The different connection modes are available due to priority and battery concerns.

#### rest-p2p

This is the default connection mode. In this mode, both nodes act as client and server (servent). When sending a command, a node acts as the client, and the other node acts as the server. This mode is unable to support commands that require streamed data. By mutual agreement it is possible to turn this mode into a virtualized client-server model where one of the nodes does not respond to requests (although the capability to recieve them cannot be turned off).

#### wss
This connection mode is able to take full advantage of Serenity. This is full duplex bidirectional comms mode utilizing websockets. Nodes are able to stream data over this connection mode. One of the devices in the connection is required to send heartbeats to the other node periodically, which it expects to be acknowledged. Exactly which device will send the heartbeats and which device will acknowledge is dictated by mutual agreement. 

### Commands

Command dispatching and handling is done seperately from communications. Serenity's command framework (Brigadier) is a deriviative of commands.py. However communications is heavily depended on commands for general upkeeping. 
Generally, there are two kinds of commands- application commands, and connection commands. Connection commands are managed by the core system framework, and are used to manage the connection.

A command in Serenity is very akin to a HTTP web request. A node will advertise the suite of application commands it supports. Least for some common functionality, these commands are highly platform specific. While the core communication protocol of serenity is platform independent, the difference of application commands help serenity provide specialized functions.

### Examples 

```json
# An application command sent over wss to get a stream of sensor readings of a device
{
	"op" : "COMMAND",
	"id" : "4e04ad51c015",
	"name" : "get_sensor_readings",
	"args" : {
		"sensors" : ["Device Orientation"],
		"readings" : "-1" 
	}
}

# The 5th response may look like this 
{
	"op" : "COMMAND_RESPONSE_STREAM",
	"id" : "4e04ad51c015",
	"result" : {
		"Device Orientation" : 3
	},
	"idx" : 4
}

# The requester may request to close the stream
{
	"op" : "CLOSE_COMMAND_STREAM",
	"id" :"4e04ad51c015"
}

```

```json
# A change connection mode request sent over rest-p2p
{
	"op" : "CHANGE_CONNECTION_MODE",
	"mode" : "wss",
	"arguments" : {
		"route" : "wss://<ip>:<port>/serenity/gateway",	
	}
}
```

```json
# A command issued by a node over rest-p2p notifying that it will assume the role of a client
# and will not respond to commands
{
	"op" : "P2P_MODE_SERVER_CLIENT",
	"client" : "self"
}

# If the other node disagrees, it may respond ith a nogo and close the connection
{
	"accepted" : false
}

```
### REST P2P Connection Opcodes

COMMAND - Issues an application command
CHANGE_CONNECTION_MODE - change connection mode to something else
SET_SERVER - assign either of the nodes as server
SET_SERVENT - change (if valid) the connection mode to servent
PING - ping the other node
RECONNECT - requests the other node to close the connection and launch a new connection with the node (regardless of uid precedence)
